### Acción 1 · WP-201 · el fix del CONTENT-TYPE

**Dónde entrar**
n8n → workflow **`beckham_bot`** (`nhOwpiGxikeU5DLR`).

**Antes de nada: anotar el rollback**
El `versionId` actual es `aa19146c-32a9-4ef4-99b4-b172685985a9`. Apúntalo. Es lo único que necesitas para
volver atrás.

**Qué elemento seleccionar**
El nodo **`Validar y Normalizar`** (es el segundo de la cadena de abajo:
`Webhook_Upsert_Expediente → Validar y Normalizar → ¿Datos Válidos? → …`).
Es un nodo Code. **No** es el de `Preparar_Prompt` ni el de `Formatear_conversacion1`.

**El código exacto que hay que pegar**
Sustituye **solo la primera línea** actual, que es exactamente esta:

```js
const body = $input.first().json.body || {};
```

por este bloque:

```js
// ── WP-201 · parseo defensivo del body ────────────────────────────────────────
// El Data Connector de Intercom manda application/x-www-form-urlencoded con el
// JSON entero como ÚNICA CLAVE del body, así que body.user_id sale undefined.
// Verificado en las ejecuciones 8052012 y 8052018 (27/07).
// La guarda `body.user_id === undefined` hace que esto sea un no-op cuando el
// body ya llega como JSON nativo → cero riesgo de regresión.
let body = $input.first().json.body || {};

if (body && typeof body === 'object' && !Array.isArray(body) && body.user_id === undefined) {
  const keys = Object.keys(body);
  if (keys.length === 1) {
    // dos candidatos: la clave sola, y clave=valor por si el JSON llevaba un '='
    const candidatos = [keys[0], keys[0] + '=' + body[keys[0]]];
    for (const c of candidatos) {
      try {
        const parsed = JSON.parse(c);
        if (parsed && typeof parsed === 'object' && !Array.isArray(parsed)) {
          body = parsed;
          break;
        }
      } catch (e) {
        // no era JSON: se deja el body tal cual y la validación decidirá
      }
    }
  }
}
// ──────────────────────────────────────────────────────────────────────────────
```

**Ojo con una cosa:** la línea original usa `const body`. El bloque nuevo usa `let body` porque hay que
reasignarlo. Si dejas `const`, el nodo peta con `Assignment to constant variable`.

**Todo lo demás del nodo no se toca.** `toIsoDate`, `toBool`, la validación y el objeto `fields` se quedan
exactamente como están.

**Qué guardo**
Guardar el workflow (`Save`). **Y nada más.**

**Qué NO publico**
**No** toques `Publish`. **No** toques `Active`. **No** cambies el `path` del webhook. **No** toques ningún
otro nodo — en particular `Respond Error` sigue devolviendo `{ok:false, error}`: cambiar la forma del error
a `{resultado:"schema_error"}` es un segundo cambio y se hace en WP-206/WP-207, no ahora. Dos cambios y una
sola prueba ⇒ la prueba no cuenta.

**Resultado esperado**
Con el borrador guardado y sin publicar, el webhook de **producción** sigue ejecutando la versión vieja. Así
que el primer curl te va a dar **FAIL a propósito**: eso confirma que el guardado no publica nada.
Después de publicar, el curl `urlencoded` debe devolver `{"ok":true,...,"record_id":"rec…"}`.

**Cómo lo reverto**
n8n → `beckham_bot` → historial de versiones → restaurar `aa19146c-32a9-4ef4-99b4-b172685985a9`.
El código original queda escrito arriba en este mismo fichero, así que no se pierde.

**Qué dato me devuelves**
1. El `versionId` nuevo que aparece tras guardar.
2. Confirmación de que el nodo no muestra error de sintaxis en el editor.

Cuando me confirmes lo anterior, esto es lo que se publica y lo que arriesga:

**Qué se publica exactamente:** una versión nueva de `beckham_bot` en la que **un solo nodo** cambia, y
dentro de ese nodo **solo la primera línea** se ha convertido en un bloque que intenta un `JSON.parse`

**Qué NO cambia:** ni la URL del webhook, ni las credenciales, ni los otros 39 nodos, ni la cadena del
agente, ni los nodos desactivados de arriba.

**Riesgo:** bajo y acotado a n8n.
- El único camino nuevo se activa **solo** si `body.user_id` es `undefined` y hay exactamente una clave. Con
  un body JSON normal, el bloque no se ejecuta.
- El `try/catch` significa que un body raro no rompe: se deja tal cual y la validación devuelve el 400 de
  siempre.
- Se publica un workflow **activo en producción**. Si algo saliera mal, el efecto sería que el webhook de
  upsert siga devolviendo 400 — es decir, exactamente lo que ya hace hoy. No hay escenario en el que esto
  escriba datos peores que los actuales.

**No publico hasta que me digas explícitamente que sí.**
